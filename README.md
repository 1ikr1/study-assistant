# 个人学习助手（study-assistant）

> 一句话：**模型负责理解，算法负责调度。**
> 「今天该复习什么」交给可复现的间隔重复算法，「怎么讲给我听」才留给大模型。

这是你简历上的第二个项目。第一个（Adaptive-rag 电商客服）练的是
**检索链路 + 复杂度路由 + 风险闸门**；这一个练的是
**单 Agent + Skill + 算法内核 + 人在回路**，两块拼起来正好覆盖 Agent 应用的两大形态。

---

## 一、先讲清楚：这个项目到底解决什么问题

备考的人真正卡住的地方不是"没有资料"，而是这三件事：

1. **不知道该复习什么**——资料一堆，全看一遍时间不够，不看又心慌。
2. **不知道什么时候该复习**——凭感觉复习，结果熟的地方反复看，生的地方一直躲。
3. **不知道还剩多少活**——离考试 60 天，每天背多少心里没数，越临近越崩。

所以这个项目的主线是 **三个问句**：

| 用户问 | 谁来回答 | 为什么 |
| --- | --- | --- |
| 今天该复习什么 | 算法（查到期队列） | 是可计算的确定性问题，不该问模型 |
| 这张卡下次什么时候出现 | 算法（SM-2） | 必须可复现、可测试、可重放 |
| 我这道题为什么错了，帮我讲一遍 | 大模型（Phase 2） | 这才是模型擅长的语言活 |

**核心设计判断：把"算"和"说"分开。** 凡是能用确定性代码算出来的，绝不交给大模型。

## 二、三个关键设计决策（面试最容易被追问的地方）

### 决策 1：复习调度用算法，不用大模型

一开始很容易想：「让模型读一遍我的答题记录，直接告诉我明天复习哪几张」。
这条路看着省事，但有三个致命问题：

- **不可复现**：同样输入，模型两次给的答案不一样。调度是"每天都要跑"的东西，漂移一次就是错的。
- **不可测试**：算法可以写单元测试（本项目 38 个），模型输出没法断言。
- **不可重放**：三个月后算法升级了，你没法用历史数据回放对比效果——因为当时的"推理过程"没存下来。

所以这里用 **SM-2**（SuperMemo-2，间隔重复的经典算法）。它只有三个变量：

| 变量 | 含义 | 初始值 |
| --- | --- | --- |
| `ef` | Easiness Factor，难度系数。越大说明这张卡对你越"容易" | 2.5 |
| `interval_days` | 当前复习间隔（天） | 0 |
| `repetitions` | 连续答对次数 | 0 |

更新规则（`study_assistant/sm2.py`）：

```
评分 >= 3（算答对）：
    第 1 次答对 → 间隔 1 天
    第 2 次答对 → 间隔 6 天
    之后每次   → 间隔 = 上次间隔 × ef
评分 < 3（算答错）：
    间隔重置为 1 天，连续答对次数归零
ef 无论如何都更新：
    ef = max(1.3, ef + 0.1 - (5 - rating) × (0.08 + (5 - rating) × 0.02))
```

这个公式里有两个**刻意的保守设计**，值得单独说：

- **惩罚不对称**：答对最多加 0.10，答错最多扣 0.80。宁可复习得频繁一点，也不要漏掉一张快忘的卡。
- **EF 有下限 1.3**：防止一张卡被反复答错后，EF 掉到接近 0，变成"每天都要复习"，直接压垮整个队列。

**为什么是 SM-2 而不是 FSRS？** FSRS 效果更好，但需要大量历史数据来拟合参数，
冷启动阶段反而不如 SM-2 稳。表结构里已经预留了 `stability` / `difficulty` 两个字段，
Phase 3 攒够数据后可以平滑切换——而且因为有 `review_logs`，可以**用历史日志回放对比两套算法**。

### 决策 2：个人画像直接查，不走检索

「我每天只有 60 分钟」「我喜欢看例题」这类信息，字段是**有限且确定**的，
所以直接存在 `profile` 表里，用 `SELECT` 取，**不要**塞进向量库做语义检索。

理由是成本与可靠性完全不对等：查字段是微秒级的确定操作，向量检索是毫秒级且可能检索错。
一个"每天 60 分钟"的需求，如果因为语义相似度差了一点没被召回，用户体验就是直接崩。

这个字段也确实在参与计算——`due` 命令会用它算出今天最多该复习几张：

```
每天可用 60 分钟 ÷ 每张 1.5 分钟 ≈ 40 张
```

### 决策 3：人在回路 —— 打分先进暂存区

复习打分这件事，一旦写错就会污染整个调度队列（比如手滑把"很熟"打成"完全不会"，
这张卡的间隔会被重置，接下来几天都白复习了）。

所以加了一层**暂存区**：打分先写进 `staging_reviews` 表，状态是 `pending`，
**不碰记忆状态**；用户确认之后才真正落库。

这里还埋了一个并发保护——用**条件 UPDATE 做原子抢占**：

```sql
UPDATE staging_reviews SET status = 'confirmed', confirmed_at = ?
 WHERE id = ? AND status = 'pending'
```

只有还处于 `pending` 的记录能更新成功，靠 `rowcount == 0` 判断"已经被处理过了"。
于是同一条记录即使被点两次、或者两个请求同时到达，也只会落库一次。
**这不是为了炫技，而是"确认按钮被重复点击"是这个界面里几乎必然发生的事。**

## 三、数据模型：9 张表，分三层

```
业务数据层    subjects ──< cards ──1:1── card_state
                科目          卡片          记忆状态（算法的输出，被反复更新）

              tasks
                任务（今天打算做什么，和"要记住什么"是两回事）

事实日志层    review_logs       复习日志（只增不改）
              focus_sessions    专注记录（只增不改）

辅助层        profile（画像） / staging_reviews（人在回路） / memories（对话记忆）
```

注意 `tasks` 和 `cards` 的区别，这是这个项目里最容易混的一点：

| | 回答的问题 | 谁产生 | 例子 |
| --- | --- | --- | --- |
| `cards` | 我要**记住**什么 | 教材 / 错题 | "Dijkstra 的适用条件" |
| `tasks` | 我要**完成**什么 | 你自己安排 | "二叉树遍历 20 题，40 分钟" |

一张卡会被反复复习几十次；一个任务做完就结束了。混在一起的话，
"今天完成了几件事"和"今天复习了几张卡"永远算不清。

其中 **`review_logs` 是整个项目的"账本"**，它除了记「第几张卡、打了多少分」，
还额外记下了**当时的算法状态**：

```
elapsed_days      距上次复习过了几天
scheduled_days    当时计划隔几天
ef_before         这次复习之前的 EF
interval_before   这次复习之前的间隔
algorithm         用的哪套算法（'sm2'）
```

为什么多此一举？因为**没有这些字段，将来就没法重放**。
半年后你想验证"换成 FSRS 是不是更好"，只要拿这份日志重新跑一遍，
就能在同一批输入上对比两套算法——这是 A/B 对比能成立的前提。

```
│   ├── repo.py       数据访问层，所有 SQL 都收在这里

│   ├── coach.py      讲题：划清"算法判断"和"模型表达"的界线

│   │   ├── workers.py      4 个子 Agent：2 个纯代码，2 个用模型
│   │   ├── supervisor.py   主 Agent：分级判定 + 任务拆分
│   │   ├── graph.py        把计划编译成 LangGraph 图
│   │   └── orchestrator.py 首尾处理：降级 / 缺料 / 取成品
│   ├── ui.html       工作台界面（HTML + CSS + 原生 JS，没有构建步骤）
│   ├── desktop.py    原生窗口界面（tkinter，零下载）
│   ├── icon.ico      应用图标（16/32/48/64/128/256 六种尺寸）
│   └── icon.png      同一张图的 256×256 版本
├── data/

│   └── study.db            运行时生成的数据库
├── tests/
│   ├── test_sm2.py    算法测试（间隔规则 / EF 调整 / 可复现性 / 参数校验）
│   ├── test_repo.py   数据层测试（导入 / 复习 / 人在回路 / 画像统计）

│   ├── test_web.py    网页后端测试（真起服务器、真发 HTTP 请求）
│   └── test_desktop.py 原生窗口测试（不 mainloop，直接调方法）

└── README.md
```

**分层的意义**：`sm2.py` 是纯函数，输入输出完全确定，所以能单独测；
`repo.py` 收拢所有 SQL，将来换 SQLAlchemy 或换数据库只改这一个文件；
`view_model.py` 把"查数据"从界面里抽出来，于是**四个壳拿到的是同一批数字**；
四个界面文件只负责把数据画出来，业务逻辑一行都没有。

这条分层不是一开始就设计好的 —— 是写完终端版和网页版，发现两边开始各算各的，
才回头抽出来的。抽完的回报：后来新增 tkinter 界面时，业务代码**一行都没改**。

### 桌面快捷方式为什么完全没有窗口

快捷方式**不是**指向 `study.cmd`，而是直接指向 `pythonw.exe`：

| 快捷方式字段 | 值 |
| --- | --- |
| 目标 | `...\Python313\pythonw.exe` |
| 参数 | `-m study_assistant.web` |
| 起始位置 | 项目目录（`-m` 要靠它找到包） |

为什么要这样？因为 Windows 的 exe 文件头里有一个字段写着它属于哪种子系统：

| 子系统 | 系统行为 | 谁是这样 |
| --- | --- | --- |
| `CONSOLE` | 启动时自动配一个控制台窗口 | `python.exe`、`cmd.exe` |
| `WINDOWS` | 不配，程序自己负责画界面 | `pythonw.exe` |

所以：

- 快捷方式 → `pythonw.exe` → **一个窗口都不会出现**；
- 双击 `study.cmd` → 系统先给 `cmd.exe` 开一个控制台 → **会闪一下**（那一闪是
  `.cmd` 自己的，不是 Python 的）。

`study.cmd` 保留下来是给**终端**用的 —— 在终端里跑，窗口本来就在那儿，
不存在"闪"这回事，而且它还能接参数（`.\study.cmd stats`）。

> 顺带一提：商业软件之所以没有黑窗口，用的就是同一个道理 ——
> 编译时候选 `WINDOWS` 子系统，或者用 Electron 把运行时打包进一个 GUI 进程。
> 不是它们没有后台进程，是那个后台进程没有控制台。

### 为什么界面开在浏览器里，怎么让它看起来像独立软件

因为这个界面是网页（HTML/CSS/JS），而网页需要有人来画。选择只有一个：
**谁来当那个渲染引擎**。四条路：

| 做法 | 长什么样 | 代价 |
| --- | --- | --- |
| 用浏览器标签页打开 | 有地址栏、有标签页，一看就是个网页 | 0 |
| **用浏览器"应用模式"打开** | 没有地址栏、没有标签页，像个独立软件 | 0 ← 本项目用这条 |
| 把浏览器打包进程序（Electron / WebView2） | 真·独立软件 | 体积几十 MB 起，打包流程复杂 |
| 不用网页，用原生 GUI 重新画（tkinter / PyQt / WPF） | 真·原生窗口 | 界面要重写一遍，排版能力差很多 |

第二行是本项目的选择，实现只有一行参数：

```python
subprocess.Popen([exe, f"--app={url}", "--window-size=1180,820"])
```

`--app=` 是 Chromium 系浏览器（Edge / Chrome）自带的能力：**用独立窗口打开
这个网址，但把它所有的浏览器痕迹都藏起来**。界面的 HTML 一个字都不用改。

`study_assistant/web.py` 里的 `find_app_browser()` 会先查注册表
（`App Paths\msedge.exe`）再翻常见安装目录，找得到就用应用模式，找不到就老实
退回普通标签页 —— 所以换一台没装 Edge 的电脑也能用。

想强制用普通标签页看一眼对比效果：

```powershell
python -m study_assistant.web --plain-browser
```

**什么时候才真该上 Electron？** 当你需要这些的时候：开机自启、
系统级快捷键、托盘图标、读本地文件、离线可用、或者界面里要嵌入系统原生控件。
在那之前，套一层浏览器窗口是性价比最高的做法 —— 这也正是很多
"看起来像桌面软件"的程序真实的样子。

### 窗口尺寸：默认最大化，不默认全屏

实际的启动参数：

```
msedge.exe
  --app=http://127.0.0.1:8765/
  --user-data-dir=%LOCALAPPDATA%\study-assistant\browser-profile
  --no-first-run --no-default-browser-check
  --start-maximized
```

**为什么默认不是全屏**（这是踩坑换来的结论）：

> `--start-fullscreen` 交给**浏览器**去管全屏，页面就失去了控制权。
> 这种情况下 `document.fullscreenElement` 是 `null`，页面**没有办法**退出它 ——
> 用户只能按 `F11` 或 `Alt+F4`。一个"退不出去"的默认值是糟糕的默认值。

而默认最大化几乎没有损失：铺满屏幕、只留任务栏，和全屏看起来差不多，
但可以随便拖、缩、关。加上主题换成浅色之后，那条标题栏和界面是同一个色系，
也不再有"白条突兀"的问题。

想全屏就点侧边栏的「全屏显示」—— 这条走的是**页面自己的 Fullscreen API**，
`Esc` 或再点一次就能退出来，控制权始终在页面手上。

### 那个 `--user-data-dir` 是干什么的

这是踩坑才加上的，不加的话**所有启动参数都会被丢掉**：

> Edge 已经在后台运行时，再启动 `msedge.exe` 只是**给老进程发一条消息**说
> "再开个窗口"，然后自己立刻退出。命令行参数在这一刻被丢掉，
> 新窗口按老进程的默认设置开。
>
> 给它一个独占的配置目录，Edge 就没法复用老进程，只能新起一个，参数才生效。

顺带两个好处：任务栏图标不和你的个人 Edge 挤在一起，更像独立软件；
关掉窗口那个进程就退出，不会留一堆后台。

配置目录在 `%LOCALAPPDATA%\study-assistant\browser-profile`，几十 MB。
不想要了直接删掉，下次会重建。

### 如果确实要用 `--fullscreen`

```powershell
python -m study_assistant.web --fullscreen
```

这时窗口是全屏的，而且**页面退不出来**（原因见上面）。逃生口：

- 按 `F11` 切换全屏 —— 这是浏览器的开关
- `Alt+F4` 直接关窗口

页面会检测这种情况（窗口铺满屏幕、但自己没拿到全屏状态），
在侧边栏底部显示一行提示，不会让人莫名其妙卡在里面。

### 「关闭应用」到底关了什么

它会做两件事，顺序是有讲究的：

1. **先把界面切到「正在退出…」**，然后才发关闭请求。
   顺序反过来的话，服务先停了、请求失败，用户看到的第一反应就是
   "连接失败" —— 可这明明是一次**成功**的关闭。
2. **关掉后台服务，然后关掉浏览器窗口。**

第 2 条修的是一个更根本的问题：原来「关闭应用」只停后台，窗口还留在那儿，
里面显示一个连不上的页面 —— **那不叫关闭应用，那叫拔电源。**

更麻烦的是，全屏是浏览器管的（见上），页面自己退不出来。
所以"从外面把窗口关掉"这个出口必须有。

实现上：启动浏览器时记下它的进程号，关闭时用 `EnumWindows` 找到属于这个进程的
顶层窗口，发一条 `WM_CLOSE`。找不到就按窗口标题兜底
（启动器进程和真正的浏览器进程偶尔不是同一个）。整条链路上任何一步失败都只返回 0，
不会抛异常 —— 关闭流程里炸掉，用户就会卡在一个关不掉的窗口里。

> 注意：用 `--plain-browser`（在你自己的浏览器里开标签页）时，
> **不会**去关你的浏览器 —— 那里面还有你自己的标签页。所以那种模式下不记进程号。

另外还有两层保底：

1. URL 上带 `?fullscreen=1` 时，页面**埋伏一个监听**：用户第一次点任何地方
   才调 `requestFullscreen()`。这是被浏览器规则逼的 —— **全屏必须由用户操作触发**，
   页面一加载就自己调会被拒绝。
2. 配置目录万一建不出来（没权限、盘满），只退化成"带标题栏的应用窗口"，
   不会连应用窗口都不开。

### 图标是怎么来的

图标是**算出来的**，不是找的：`work/make_app_icon.py` 用纯标准库手写。

- 形状用**有符号距离场**（SDF）描述，边缘按像素覆盖率做防锯齿 —— 不是画完再模糊；
- 先渲染一张 512×512 主图，再**盒式降采样**出 16/32/48/64/128/256 六档；
- `.ico` 就是一份目录 + 六张 PNG，自己拼的。

为什么要这个流程：Windows 任务栏用 32、Alt+Tab 用 48、桌面大图标用 256。
**如果只有一张 256 让系统自己缩，16 和 32 那两档会糊。** 每档独立降采样才清楚。

设计上：圆角方块 + 祖母绿对角线渐变 + 左上柔光 + 白色沙漏。
沙漏对应「专注计时」，也是工作台视觉上的主角；选绿色是因为它在深色和浅色任务栏上都跳得出来。
网页的 favicon 是同一套设计的 SVG 内联版本，这样缩放任何倍率都锐利。

### 主题：默认浅色，可切深色

颜色全部收在 CSS 变量里，分两套：

```css
:root      { --bg:#f4f6f8; --panel:#ffffff; --fg:#171b20; ... }  /* 浅色，默认 */
html.dark  { --bg:#0b0f14; --panel:#141a21; --fg:#e6edf3; ... }  /* 深色 */
```

切主题只是给 `<html>` 加一个 class，**不需要重渲染页面，也不需要重算任何数据** ——
因为换的是变量的值，不是规则。选过的偏好存在 `localStorage` 里。

一个容易踩的坑：SVG 的**表现属性**（`stroke="#..."`）读不到 CSS 变量，
必须写成类然后在 CSS 里 `stroke: var(--x)`。所以沙漏的框架是 `.glass-frame { stroke:var(--glass-line) }`。

> 终端版和 tkinter 版还是深色。它们没有 CSS 变量这层，要跟着改得手动换色值。

## 七、跑测试

```powershell
cd C:\Users\yv\Documents\Codex\study-coach
$env:PYTHONIOENCODING = "utf-8"
& "$env:LOCALAPPDATA\Programs\Python\Python313\python.exe" -m unittest discover -s tests -v
```

当前 **160 个测试全过**。测试覆盖的重点不是"代码跑不跑得通"，而是几个**容易悄悄写错的地方**：

- 连续满分时，间隔必须是 `1 → 6 → 16`（第三次是 `6 × 2.7 = 16.2`，四舍五入到 16）
- EF 有下限，反复答错也不能低于 1.3
- 答错后间隔必须重置为 1 天、连续答对次数归零
- **同样输入必须得到同样输出**（同一个状态跑 100 次结果完全一致）
- `preview` 不能修改原状态（否则预览一次就等于复习了一次，这是很隐蔽的 bug）
- 暂存记录确认两次，第二次必须被拒绝
- 丢弃暂存后，`review_logs` 必须一条都没多
- 交互式菜单里走完一遍"开始复习"，`review_logs` 必须真的多一条
  （交互程序最常见的问题就是"看起来在跑，其实什么都没干"）
- 预览界面看一百次，`card_state` 必须一行都没变
- 同一个端口不能被两个服务同时绑住（Windows 的 `SO_REUSEADDR` 会允许，很坑）
- 调了 `/api/shutdown` 之后，服务器必须真的停下来
- 专注记录只算当天：昨天跑的 25 分钟不能算进今天的进度
- 被打断的专注（只跑了 7 秒）也要记下来 —— "专注了多久"和"完整跑完几轮"是两件事
- 画像里被填了"不知道"，整个看板不能崩
- 默认全屏那几个启动参数必须拼对（尤其是那个决定性的 `--user-data-dir`）
- 配置目录建不出来时，只能退化成"带标题栏的应用窗口"，不能掉到普通浏览器标签页
- **答对了不该调用大模型** —— 连一次网络请求都不该发出去（假传输层会记账）
- 模型返回的"看起来像响应"的东西（`choices` 空数组、`content` 是 null）必须当错误抛出来，
  否则上层会拿到空字符串，当成模型说了句"什么都没有"
- 中文必须以 UTF-8 而不是 `\uXXXX` 转义发出去 —— 两者都合法，但后者让抓包完全看不懂

## 八、技术选型

| 层面 | 选型 | 为什么是它 |
| --- | --- | --- |
| 语言 | Python 3.11+ | — |
| 存储 | SQLite | 单机单用户，零运维。表结构写清楚了，要换也不痛 |
| 调度算法 | 自己实现的 SM-2 | 确定性计算，必须可复现、可测试、可重放 |
| 命令行 | `argparse` | 标准库够用，换成任何 CLI 框架都没收益 |
| **HTTP 层** | **FastAPI + uvicorn** | 接口涨到十几个之后，手写路由就没收益了；顺带白拿请求校验、SSE、并发、`/docs` |
| **编排层** | **LangGraph** | 每次请求的图形状不同（节点和边来自计划），还要并行分支和事件流 |
| 大模型调用 | 标准库 `urllib` | 就是一个 HTTP POST，装 SDK 只是包装 |
| 测试 | `unittest` + `TestClient` | 标准库够用；`TestClient` 让接口测试不用起真服务器 |

**选型原则：按场景适配度，不按"能不能用标准库"**。

这条是踩过弯路的。最早我给项目定了一条"零依赖"的规矩，于是：
用 `http.server` 手写路由、用 `tkinter` 画界面、用 `urllib` 调模型。
前两个后来都换掉了 —— 不是因为它们不 work，而是**当需求涨到十几个接口、
还要 SSE 流式输出时，自己维护这一层已经没有收益了**。

反过来，SM-2 和 SQLite 一直没换：它们算的是确定性的东西，
换任何框架都不会更好。

所以判断标准是：**这东西解决的这个场景，它是不是最合适的？**
能白拿能力就上框架，白拿不到就别上。

## 九、下一步路线

### Phase 2 · 接大模型与多 Agent

关键判断：**不是所有事都值得开一个 Agent。**

| 子 Agent | 是否用大模型 | 理由 |
| --- | --- | --- |
| Scheduler（排复习计划） | 纯代码 | 已经由 SM-2 算出来了，模型只会把它搞乱 |
| Stats（统计与预测） | 纯代码 | 同上，`stats` / `forecast` 已经是确定性答案 |
| Knowledge（讲解知识点） | 用模型 | 需要组织语言，这正是模型的活 |
| Parse（把教材/错题转成卡片） | 用模型 | 非结构化 → 结构化，典型的模型任务 |
| Report（生成周报） | 用模型 | 汇总 + 成文 |

只有出现「**查资料 + 算数据 + 出成品**」这类需要两件以上不同能力协作的请求时，
才升级到多 Agent 编排；单个请求走单 Agent + Skill 就够了。

#### 已完成：Knowledge（讲题）

答错之后，复习页会多出一块「上一张」，点「让 AI 讲一遍」就行。

这一块的重点不在"能调通接口"，而在**它划的界线**：

```python
def should_explain(rating: int) -> bool:
    return rating in {0, 1, 2}      # 只有答错才值得花一次调用
```

这个判断是**纯算法**做的，而且它决定了要不要花钱。答对了还去调模型，
除了浪费，模型还会"硬找问题"，给已经答对的学生添乱。

`build_explain_messages()` 也是纯函数 —— **prompt 是产品逻辑的一部分**，
所以它不该散落在发请求的地方（改一句话没人知道）。现在它可以逐字断言。

给模型的东西里有两样是别的项目里容易漏的：

- **这张卡他答错过几次** —— 答错 3 次和第一次答错，该讲的不一样
- **画像里的学习偏好** —— "喜欢看例题，不爱看大段文字"会作为一句话进 prompt

#### 技术选型：为什么没装 SDK

DeepSeek 的接口就是 OpenAI 那套，而**调大模型就是一个带 Authorization 头的
HTTP POST**，返回的 JSON 里取出 `choices[0].message.content`。
标准库的 `urllib.request` 完全够用 —— 零依赖这条底线保住了，
顺便也就看清了那些 SDK 到底替你做了什么。

`ChatClient` 留了一个**可注入的 transport**。测试时换成假的，于是：

- 不烧 token
- 不依赖有没有网
- 能测错误分支 —— 401、非 JSON、`choices` 是空数组这些，真实接口很难复现

#### 配置 API key

在项目根目录的 `.env` 里写（`init` 会自动生成这个文件）：

```
DEEPSEEK_API_KEY=你的密钥
```

`.env` 已经在 `.gitignore` 里 —— **key 绝对不能进仓库**。
没配也能跑，只是那个按钮会提示你先配置。

### Phase 3 · 从"能用"到"像个产品"

网页界面第一版已经做好了（复习 / 统计 / 负载 / 画像 四个页签，
逐步确认模式和暂存区都在里面）。后面还能加：

- **SSE 流式输出**：等接入大模型之后才有意义——"正在思考…"要一个字一个字蹦出来，
  用户不能等十秒才看到第一个字。这也是第一个项目里练过的东西，正好对比
  标准库和 FastAPI 各自要写多少代码。
- **记忆召回**：`memories` 表 + 相似度召回，让助手记住"我晚上效率高"这类偏好。
- **评测集**：准备一批标准问题，量化"加了大模型之后到底涨了多少"。

## 十、可以写进简历的点

1. **把可计算的部分从模型里剥离出来**：复习调度用 SM-2 纯算法实现，
   保证可复现、可测试、可重放；模型只负责语言生成。
2. **为算法可重放而设计日志**：`review_logs` 额外记录 `ef_before` /
   `interval_before` / `elapsed_days` / `algorithm`，使算法升级后可做 A/B 对比。
3. **人在回路 + 原子抢占**：复习打分先进暂存区，用条件 UPDATE 实现
   同一条记录只能确认一次，避免重复点击污染调度队列。
4. **画像直接查询而不走检索**：把"有限且确定"的字段从向量库里拿出来，
   降低延迟与不确定性。
5. **38 个单元测试覆盖算法边界**：不对称惩罚、EF 下限、可复现性、
   `preview` 不产生副作用等隐蔽问题。
